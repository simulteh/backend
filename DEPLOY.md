# Обновление существующей ВМ

Это **план поэтапной работы**, а не разрешение запускать команды целиком.
По решению пользователя обновление сервиса в разработке выполняется без
резервных копий, дампов и сохранения старых образов под отдельными тегами.
Правило об изменениях на ВМ сохраняется: сначала согласуем конкретный набор
действий, затем выполняем его. Одно подтверждение может охватывать весь
описанный этап; повторно согласовывать каждую входящую в него команду не нужно.
При ошибке следующий этап не запускаем. Инструкция относится к проекту
`/root/net-genius`:

Согласованный порядок: сначала разворачиваем и проверяем бэкенд и Swagger,
после этого команда фронтенда адаптирует интерфейс по опубликованному API.
Готовность фронтенда не является условием обновления бэкенда. До адаптации
часть существующего интерфейса может не работать с новым API.

```text
/root/net-genius/
├── docker-compose.yml     ← запускает все четыре сервиса
├── backend/              ← Git-репозиторий бэкенда
│   ├── Dockerfile
│   └── .env              ← новые настройки почты, JWT и администратора
├── frontend/
└── nginx/nginx.conf
```

Сервисы уже называются `nginx`, `frontend`, `backend`, `database`.
Nginx работает **в контейнере** и обращается к `backend:8080`.
Бэкенд обращается к `database:5432`. Снаружи открыты только порты nginx 80/443.
Существующая PostgreSQL 15 хранит данные в volume `postgres_data`.

Команды ниже выполняются **из `/root/net-genius`**, даже если меняются файлы
бэкенда. Все команды с `docker compose` используют корневой Compose.
`backend/docker-compose.yml` — отдельный вариант запуска бэкенда с новой БД;
на этой ВМ его не используем. Отсутствие этого файла в старом клоне было
локальным удалением (`D` в `git status`). После `git restore` он может вернуться,
но запускать его здесь не требуется.

## 1. Проверить текущее состояние

Проверки ниже только читают состояние. Актуальные исходники фронтенда находятся
на ВМ; в этом обновлении их не копируем локально, не сбрасываем и не меняем.
При последней проверке было свободно около 3 ГиБ. Перед сборкой проверьте место
снова. Очистка Docker не входит в этот план и автоматически не выполняется.

```bash
cd /root/net-genius
df -h /root
docker compose ps
git --no-optional-locks -C backend status --short --branch
```

## 2. Отбросить старые изменения кода и получить новую версию

До сброса файлов перенесите нужные действующие настройки почты из старого
`application.properties` в `backend/.env` на самой ВМ. Секреты не выводятся
в чат и не переносятся на локальную машину. Существующий `.env` сначала
проверяется без вывода значений; при наличии настроек они сохраняются.

Удаление незакоммиченных изменений **только в клоне бэкенда на ВМ** входит
в согласуемый этап обновления. Перед выполнением требуется подтверждение
этого этапа пользователя.
Фронтенд не сбрасываем и его файлы локальной копией не заменяем. Команда `restore`
возвращает отслеживаемые Git-файлы к последнему коммиту; неотслеживаемые файлы
не удаляет. Корневой Compose, nginx и PostgreSQL эта команда не меняет.

Подготовленная версия находится в ветке `codex/vm-deploy`. Её можно развернуть
прямо из этой ветки; предварительное слияние в `main` не требуется.
Для текущего клона, в котором локальная ветка `codex/vm-deploy` ещё не создана,
после подтверждения обновления файлов на ВМ:

```bash
cd /root/net-genius
git -C backend restore --source=HEAD --staged --worktree -- .
git -C backend status --short --branch
git -C backend fetch origin codex/vm-deploy:refs/remotes/origin/codex/vm-deploy
git -C backend switch --track -c codex/vm-deploy origin/codex/vm-deploy
git -C backend log -1 --oneline
```

Если локальная ветка уже есть, сначала проверьте её состояние, затем используйте
`git switch codex/vm-deploy` и `git pull --ff-only origin codex/vm-deploy`.
При ошибке получения или переключения ветки остановитесь и разберите причину. Не используйте
`git clean` или `git reset --hard`. Сам `git pull` только обновляет файлы;
старый бэкенд продолжает работать в прежнем контейнере.

## 3. Заполнить настройки бэкенда

В рамках подтверждённого этапа настройки создайте файл из шаблона, если его
ещё нет, и заполните его. Если настройки уже перенесены перед сбросом кода,
дополните существующий файл:

```bash
cd /root/net-genius
test -f backend/.env || cp backend/deploy/vm.env.example backend/.env
chmod 600 backend/.env
nano backend/.env
```

`backend/.env` — настройки приложения. Он исключён из Git и Docker build context.
Пароли записывайте в одинарных кавычках, особенно если в них есть `$` или `#`.
Настоящий файл с паролями никому присылать не нужно.

| Настройка | Что указать |
|---|---|
| `JWT_SECRET` | Один раз сгенерировать `openssl rand -base64 64` и вставить одной строкой |
| `SMTP_USERNAME` | Почтовый ящик отправителя |
| `SMTP_PASSWORD` | Сгенерированный пароль приложения для почты |
| `SMTP_HOST`, `SMTP_PORT` | В шаблоне Яндекс, порт 465 с SSL; сверить с вашим провайдером |
| `SMTP_FROM` | Можно оставить пустым: используется `SMTP_USERNAME` |
| `FRONTEND_URL` | `https://www.simultech.ru`; сюда ведут ссылки из писем |
| `TEACHER_REQUEST_EMAIL` | Ящик получателя заявок преподавателей |
| `ADMIN_EMAIL`, `ADMIN_PASSWORD` | Ваши email и пароль первого администратора приложения |
| `PUBLIC_API_URL` | `/api`, адрес запросов Swagger на этом сайте |
| `FORWARD_HEADERS_STRATEGY` | `framework`, с nginx из шага 6 |
| `SEED_LABS` | `false`, демонстрационные лабораторные не добавляются |

JWT-ключ сохраняйте при следующих обновлениях. Его смена завершает действие
старых access-токенов. Новый слой авторизации также потребует повторного входа
для токенов, выданных старой версией без `uid`.

`ADMIN_EMAIL` и `ADMIN_PASSWORD` используются при создании администратора.
Существующий аккаунт не получает новый пароль или роль из `.env`. Для первой
настройки выберите email, ещё не занятый обычным пользователем, либо используйте
данные существующего администратора.

### Подключить файл к существующему Compose

В `/root/net-genius/docker-compose.yml` добавьте **только `env_file`** в сервис
`backend` рядом с `build` и `environment`:

```yaml
  backend:
    build:
      context: ./backend
      dockerfile: Dockerfile
    env_file:
      - ./backend/.env
    # Существующие environment, depends_on и restart оставьте на месте.
```

Существующие `SPRING_DATASOURCE_URL`, `SPRING_DATASOURCE_USERNAME` и
`SPRING_DATASOURCE_PASSWORD` в `backend.environment` сохраняются. Они имеют
приоритет над настройками файла. Адрес остаётся
`jdbc:postgresql://database:5432/netgenius`.

В сервисе `database` сохраните прежние `POSTGRES_*` и подключение
`postgres_data:/var/lib/postgresql/data`. Значения пароля БД здесь и в бэкенде
уже согласованы; для первого обновления их не меняем. Смена переменной
`POSTGRES_PASSWORD` сама по себе не меняет пароль существующей БД.

`APP_BIND_ADDRESS`, `APP_PORT` и `POSTGRES_*` из standalone-шаблона на этой ВМ
добавлять не нужно. Новые сети, контейнер PostgreSQL и публикация порта 8080
тоже не нужны.

```bash
docker compose config --quiet
```

Это проверяет Compose, не печатая пароли. Файл `.env` сам по себе не передаётся
контейнеру: для этого и добавляется `env_file`.

## 4. Собрать бэкенд до замены работающего контейнера

После подтверждения этапа соберите новый образ. Эта операция меняет состояние
Docker на ВМ:

```bash
cd /root/net-genius
docker compose build backend
```

Работающий контейнер от сборки не меняется. Ошибка сборки не требует перезапуска
ни БД, ни фронтенда, ни nginx.

Фронтенд на этом этапе не редактируем и не пересобираем. После готовности
бэкенда команда фронтенда получит Swagger и список обнаруженных расхождений:
обращения к `http://212.67.12.82:8080`, профиль с токеном в query-параметре
и изменение профиля через `PUT /auth/profile`. Для сайта на HTTPS нужны
относительный адрес `/api`, заголовок `Authorization: Bearer ...` и
`PUT /users/profile`. Порт 8080 наружу не открываем.

Совместимые маршруты входа и регистрации помогают старому клиенту, но не
исправляют эти обращения фронтенда. Поэтому готовность бэкенда проверяем
запросами к API через Swagger или HTTP-клиент. Полный сценарий через интерфейс
проверяется позднее, после адаптации фронтенда, включая страницы
`/confirm-email?token=...` и `/reset-password?token=...` для ссылок из писем.

## 5. Подготовить старую таблицу пользователей

Проверка текущей БД только чтением показала: в ней четыре пользователя,
у всех `enabled=false`, а столбца `users.role` нет. Новая версия ожидает
обязательную роль. Поэтому до первого старта нового бэкенда нужен отдельный
ручной переход через `deploy/upgrade-legacy-users.sql`.

Скрипт добавляет столбец `role`, заполняет отсутствующие роли значением `USER`
и задаёт это значение по умолчанию. Четыре старых неподтверждённых аккаунта
получат роль `USER`. Их email, хеши паролей и `enabled=false` сохраняются:
**аккаунты не активируются**, подтверждение email по-прежнему требуется.
Имеющиеся ненулевые роли скрипт не перезаписывает.

Это реальное изменение схемы и данных, которое должно быть включено в
подтверждённый этап обновления. Новый бэкенд ещё не должен быть запущен.
Полноценный прогон этой миграции на PostgreSQL пока не выполнялся; успешный
запуск нельзя считать подтверждённым заранее.

После подтверждения, из корня проекта:

```bash
cd /root/net-genius
docker compose exec -T database sh -c 'psql -X -v ON_ERROR_STOP=1 -U "$POSTGRES_USER" -d "$POSTGRES_DB"' < backend/deploy/upgrade-legacy-users.sql
```

Ожидается успешный `COMMIT` без ошибок. `ON_ERROR_STOP=1` прекращает выполнение
при ошибке; изменения скрипта объединены транзакцией. Если команда завершилась
ошибкой, новый контейнер не запускайте. Для последующей проверки состояния
достаточно агрегированных результатов без email и хешей паролей:

```bash
docker compose exec -T database sh -c 'psql -X -v ON_ERROR_STOP=1 -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c "SELECT role, enabled, count(*) FROM users GROUP BY role, enabled ORDER BY role, enabled;"'
```

Для обнаруженных четырёх старых аккаунтов ожидается `USER`, `false`, `4`.

## 6. Обновить бэкенд и nginx

Новый бэкенд при старте дополнительно обновляет схему через Hibernate и
`db/profile-schema.sql`. Версионированных миграций пока нет. Автотесты
проверяли H2; обновление PostgreSQL и реальные сценарии на ВМ ещё не проверены.
Замена контейнера должна входить в подтверждённый этап и выполняется после
успешного шага 5.

В рамках этого подтверждённого этапа пересоздайте **только бэкенд**. Будет короткий
перерыв API:

```bash
cd /root/net-genius
docker compose up -d --no-deps --no-build backend
docker compose logs --tail=100 backend
```

БД, frontend и nginx этой командой не пересоздаются. При ошибке старта не
продолжайте настройку наугад; сохраните текст ошибки без секретов.

Готовая конфигурация `backend/deploy/nginx.vm.conf` основана на присланном
конфиге ВМ. Она сохраняет домен, сертификаты и выдачу фронтенда, добавляет
передачу `/api-docs/swagger-config` в бэкенд, заголовки прокси и размер
multipart-запроса 6 МиБ. До замены сверьте её с актуальным файлом ВМ:

```bash
diff -u nginx/nginx.conf backend/deploy/nginx.vm.conf
```

У `diff` код 1 означает найденные различия. Если после присланной версии
на сервере добавляли другие маршруты, перенесите только нужные правки в
существующий конфиг. Замена файла должна входить в подтверждённый этап. При
использовании подготовленного файла записывайте его в уже существующий
`nginx/nginx.conf`, чтобы сохранить Docker bind mount:

```bash
cat backend/deploy/nginx.vm.conf > nginx/nginx.conf
docker compose exec -T nginx nginx -t
```

Только если `nginx -t` завершился успешно и reload входит в подтверждённый
этап, перечитайте конфигурацию:

```bash
docker compose exec -T nginx nginx -s reload
```

Reload также заставляет nginx заново разрешить имя `backend` после замены
контейнера. `systemctl nginx` здесь не используется: nginx работает в Docker.

При ошибке `nginx -t` рабочий nginx продолжает использовать прежний конфиг.
Исправьте найденную ошибку в рамках согласованного этапа и повторите проверку.
Не перезапускайте nginx с невалидным файлом.

## 7. Проверить результат

```bash
cd /root/net-genius
docker compose ps
curl --fail --show-error https://www.simultech.ru/api/auth/ping
curl --fail --show-error https://www.simultech.ru/api-docs/swagger-config
curl --fail --show-error https://www.simultech.ru/api-docs
```

Ожидаются `pong`, JSON настроек Swagger и JSON схемы API. Swagger остаётся по
адресу `https://www.simultech.ru/swagger-ui/index.html`; сервер запросов — `/api`.
Прямой `curl http://127.0.0.1:8080/...` в этой схеме не подходит: порт бэкенда
не опубликован на ВМ.

Реальные сценарии создают аккаунты, токены, письма и заявки, поэтому их запуск
тоже согласуется отдельно. Через Swagger или HTTP-клиент проверьте регистрацию,
доставку письма, подтверждение email, вход и профиль. Отдельно проверьте письмо
с документом преподавателя и его одобрение администратором. Почта в тестах
подменяется; реальная доставка на ВМ автоматически не проверялась.

После проверки бэкенда передайте Swagger команде фронтенда. Проверка сценариев
через интерфейс относится к следующему этапу, после его адаптации.

Логи нужных сервисов:

```bash
docker compose logs --tail=100 backend
docker compose logs --tail=100 nginx
```

## Последующие обновления

После первой успешной настройки следующие команды остаются планом обновления.
Они не запускаются целиком автоматически: получение кода, сборка, замена
контейнера и reload должны входить в согласованный этап:

```bash
cd /root/net-genius
git -C backend pull --ff-only origin codex/vm-deploy
docker compose config --quiet
docker compose build backend
docker compose up -d --no-deps --no-build backend
docker compose exec -T nginx nginx -t
docker compose exec -T nginx nginx -s reload
```

После слияния подготовленных правок в `main` можно отдельно согласовать
переход на неё для следующих обновлений. Изменения `.env` применяются
через `up -d --no-deps --no-build backend`, а не обычный `restart`.

Не выполняйте `docker compose down -v`: ключ `-v` удаляет volume с данными.
Не меняйте имя проекта Compose и место его запуска: существующий
`postgres_data` должен остаться тем же.
