# net-genius — backend (LMS + Network Simulator)

Backend системы дистанционного обучения с десктоп-симулятором сети:
роли и RBAC, подтверждение ролей, вузы и группы, приглашения, лицензии,
лабораторные работы, синхронизация прогресса симулятора и отчётность.
Текущий контракт описан ниже и в Swagger. Первоначальная спецификация
[`LMS + Network Simulator.md`](LMS%20+%20Network%20Simulator.md) сохранена как история требований.

- [Инструкция для фронтендеров](FRONTEND_GUIDE.md): подключение API, сессии, кабинеты и примеры.
- [GitHub Actions и автодеплой](deploy/GITHUB_ACTIONS.md): push в `main` → тесты → обновление бэкенда на ВМ.

## Стек

- Java 17, Spring Boot 3.4.2 (Web, Data JPA, Security, Mail, Validation)
- PostgreSQL (рантайм), H2 (тесты)
- JWT (access 15 мин) + refresh-токены в БД (30 дней)
- Argon2 (хеширование паролей, BouncyCastle)
- springdoc / Swagger UI

## Запуск

На существующей ВМ `/root/net-genius` используется **корневой** Docker Compose
с сервисами `nginx`, `frontend`, `backend`, `database`. Бэкенд собирается из
`./backend/Dockerfile`; nginx обращается к нему по `backend:8080`, а бэкенд —
к существующей PostgreSQL по `database:5432`. Пошаговая инструкция настройки
и обновления — [DEPLOY.md](DEPLOY.md).

Для этой ВМ скопируйте `backend/deploy/vm.env.example` в `backend/.env`, заполните
почту, JWT и первого администратора, затем подключите файл через `env_file`
в существующем сервисе `backend`. Настройки БД и `postgres_data` в корневом Compose
сохраняются. Все команды Compose на ВМ выполняются из `/root/net-genius`.

Swagger: `https://www.simultech.ru/swagger-ui/index.html`, API через `/api`.
Для этой схемы задаются `PUBLIC_API_URL=/api` и
`FORWARD_HEADERS_STRATEGY=framework`; конфиг для контейнера nginx —
[`deploy/nginx.vm.conf`](deploy/nginx.vm.conf).

### Отдельный запуск бэкенда и новой БД

`docker-compose.yml` внутри репозитория бэкенда — независимый вариант с сервисами
`app` и `postgres`. На существующей ВМ его не запускаем: там уже есть база
и общий Compose. Для нового отдельного окружения из каталога бэкенда:

```bash
cp .env.example .env
chmod 600 .env
nano .env
# После заполнения настроек:
docker compose config --quiet
docker compose up -d --build --wait --wait-timeout 180
```

Именно для этого варианта `.env.example` содержит `POSTGRES_*`,
`APP_BIND_ADDRESS` и `APP_PORT`. API публикуется на порту `APP_PORT` (8080
по умолчанию), Swagger — `/swagger-ui/index.html`, проверка — `GET /auth/ping`.
PostgreSQL доступен внутри отдельной Docker-сети; данные хранятся в volume.
Реальный `.env` исключён из Git и Docker build context в обоих вариантах запуска.

### Локальный запуск без контейнера приложения

Нужны JDK 17, PostgreSQL на localhost и те же переменные окружения из `.env`.
Сам Spring Boot автоматически этот файл не читает. Если `.env` заполнен в
совместимом с shell формате (секреты в одинарных кавычках), переменные можно загрузить так:

```bash
set -a
. ./.env
set +a
mvn spring-boot:run -Dspring-boot.run.profiles=local
```

Этот вариант требует отдельно доступного PostgreSQL на localhost:5432;
ни один из описанных Compose не публикует порт базы на ВМ.
На машинах с более новой JDK используйте JDK 17 для сборки.

### Тесты

```bash
mvn clean verify
```

Основные тесты выполняются на H2 in-memory (`@SpringBootTest`, MockMvc).
Проверяются регистрация, JWT, RBAC, ротация и отзыв токенов, одноразовые ссылки,
конкурирующие транзакции, группы, оценки, заявки, письма и Swagger.
`DeploymentConfigurationTest` отдельно проверяет загрузку production-настроек
из окружения и SMTP в режимах STARTTLS/SSL. Реальную доставку писем и запуск
с PostgreSQL необходимо проверить на ВМ.

### Первый администратор

`DataInitializer` создаёт администратора из `ADMIN_EMAIL` и `ADMIN_PASSWORD`,
если такого email ещё нет. Общего пароля по умолчанию нет. При последующих
запусках пароль существующего аккаунта не перезаписывается. Демонстрационные
лабораторные создаются только при `SEED_LABS=true`.

## Роли и доступ (RBAC)

Одна роль на пользователя. Переход только `USER → STUDENT` или `USER → TEACHER`
через подтверждение администратором. Контроль доступа централизован по путям
(`SecurityConfig`):

| Префикс | Требуемая роль |
|---|---|
| `POST /auth/{register,login,refresh,logout,confirm-email,forgot-password,reset-password,resend-confirmation}`, `GET /auth/{ping,confirm}` | публично |
| `GET /groups/my`, `POST /groups/join/{inviteCode}` | `STUDENT` |
| остальные `/groups` и `/groups/**` | `TEACHER`, доступ только к своим группам |
| `GET /universities/**` | публично |
| `/admin/**` | `ADMIN` |
| `/teacher/**` | `TEACHER` |
| `/student/**`, `/sync/**` | `STUDENT` |
| прочее | аутентификация |

## Обзор API

- **Аутентификация** `/auth`: `register`, `login`, `refresh`, `logout`,
  `confirm-email`, `change-password`, `forgot-password`, `reset-password`, `me`
- **Пользователь** `/users`: `me`, `profile` (PUT), `email` (PUT)
- **Подтверждение ролей**: `/verification/{student,teacher,status}`,
  `/admin/verifications` (+ `{id}/approve`, `{id}/reject`)
- **Вузы**: `GET /universities`, `/teacher/university-request`,
  `/admin/university-requests` (approve/reject), `/admin/universities` (CRUD)
- **Группы**: `/teacher/groups` (CRUD), `/teacher/groups/{id}/invite`,
  `/teacher/groups/{id}/report`, `/teacher/students`
- **Приглашения**: `/student/invitations` (+ `{id}/accept`, `{id}/decline`)
- **Лицензии**: `/licenses/{activate,me,history}`, `/admin/licenses/{create,batch}`,
  `GET /admin/licenses`
- **Лабораторные**: `GET /labs`, `/labs/{id}`, `/labs/{id}/leaderboard`
- **Синхронизация**: `POST /sync/progress`

Полное описание — в Swagger UI.

## Личные кабинеты студента и преподавателя

Новые маршруты используют JWT и существующие таблицы групп/профилей. Регистрация
по-прежнему выдаёт `USER`; `STUDENT` или `TEACHER` назначается после проверки.
`GET /profile/me` возвращает реальную роль, поэтому до назначения там будет
`USER`, а для администратора — `ADMIN`. Пример профиля студента:

```json
{
  "id": 42,
  "role": "STUDENT",
  "avatarUrl": null,
  "lastName": "Иванов",
  "firstName": "Иван",
  "middleName": "Иванович",
  "email": "ivan@example.com"
}
```

`id` в профиле, `studentId` при добавлении/удалении и `students[].id` в группе —
**ID пользователя (`users.id`)**, а не внутренний ID профиля `students.student_id`.
Старые `/teacher/**` сохраняют свой контракт с внутренними ID профилей.

| Метод и путь | Назначение / ответ |
|---|---|
| `GET /profile/me` | Профиль; без действительного токена — JSON `ApiError`, 401 |
| `POST /profile/teacher-request` | `multipart/form-data`: `fullName`, `organization`, `file`; письмо с выпиской, 200 |
| `GET /groups` | Свои группы преподавателя: `[{id, name, organization, studentsCount}]` |
| `POST /groups` | `{name, organization}` → группа с `studentsCount: 0`, 201 |
| `GET /groups/{id}` | `{id, name, organization, inviteCode, students: [{id, lastName, firstName, scores}]}` |
| `PUT /groups/{id}` | `{name, organization}` → обновлённая группа, 200 |
| `POST /groups/{id}/students` | `{studentId}` → сообщение, 200; повторное добавление допустимо |
| `DELETE /groups/{id}/students/{studentId}` | Удаление из своей группы → сообщение, 200 |
| `POST /groups/join/{inviteCode}` | Вступление студента → группа с ФИО преподавателя, 200; повторный вызов допустим |
| `GET /groups/my` | `[{id, name, organization, teacher: {lastName, firstName, middleName}}]` |
| `POST /profile/scores` | `{level, score}` → актуальные 11 оценок, 200 |
| `GET /profile/scores` | Массив из 11 лучших оценок текущего пользователя |
| `POST /auth/resend-confirmation` | `{email}` → одинаковый публичный ответ для неизвестного и известного адреса |

Группой управляет только её преподаватель: попытка обратиться к чужой группе
даёт 404, неподходящая роль — 403. `GET /groups/my` и вступление доступны только
студентам. Код приглашения постоянный, непредсказуемый; это не семидневное
персональное приглашение старого `/teacher/groups/{id}/invite`.

Организация новой группы хранится текстом, без обязательной записи в справочнике
вузов. Старые группы также доступны: название организации берётся из их вуза,
а код создаётся при первом открытии. Ограничение на вступление в группу чужого
вуза сохраняется для старых групп с заданным `universityId`.

Оценки имеют позиции `[обучение, уровень 1, ..., уровень 10]`: `null` означает,
что результата нет, `0` — сохранённый нулевой балл. `level` и `score` — целые
числа 0–10; неверные, дробные и отсутствующие значения дают 400. Новый балл
сохраняется только если он лучше прежнего, включая одновременные запросы.
Оценки `/profile/scores` и `students[].scores` читаются из одной таблицы
`user_level_scores`. Они доступны текущему аутентифицированному пользователю
и не зависят от ID/порядка лабораторных и старого `/sync/progress`.

Заявка преподавателя требует подтверждённого email и роли `USER`. Принимаются
PDF, JPG/JPEG, PNG и DOC до 5 МиБ с проверкой расширения и сигнатуры. Документ
передаётся вложением в письмо; сервер не публикует его как доступный по URL файл.
Создаётся `PENDING`-заявка в существующей системе проверок, роль автоматически
не меняется. Администратор может рассмотреть её через
`/admin/verifications/{id}/approve` или `/reject`. Повторная ожидающая заявка
даёт 409; сбой почты — 503 с откатом заявки, чтобы можно было повторить отправку.

Старые JSON-маршруты `/verification/student` и `/verification/teacher` продолжают
принимать данные профиля для подтверждения роли. Поля `documentUrl` и
`documentType`, модель `VerificationDocument` и сохранение внешних ссылок удалены.
Для заявки преподавателя с документом используется `/profile/teacher-request`.

Настройки окружения:

- `FRONTEND_URL` — базовый URL фронтенда (по умолчанию `https://simulteh.com`).
  Письма ведут на `/confirm-email?token=...` и `/reset-password?token=...`.
- `WEBSITE_URL` — страница «Все подробности» в приветственном письме СИМУЛТЕХ.
  По умолчанию совпадает с `FRONTEND_URL`; можно задать отдельную страницу для вузов.
- `TEACHER_REQUEST_EMAIL` — получатель заявок преподавателей. Пока не задан,
  отправка заявки возвращает 503; регистрация и остальные маршруты работают.

Письмо подтверждения регистрации оформлено от имени СИМУЛТЕХ: благодарность,
информация о демо-версии и сертификации, инструкция по заявке преподавателя,
ссылка на сайт и кнопка подтверждения. Текст учитывает текущую схему ролей:
доступ как студент появляется после подтверждения статуса, а подтверждение email
само по себе не меняет `USER` на `STUDENT`. Ссылка подтверждения и ссылка сброса
пароля действуют 24 часа.

Перед запуском на существующей БД Spring выполняет идемпотентный
`db/profile-schema.sql`, снимающий старое обязательное ограничение `university_id`
у групп. Новые столбцы/таблица добавляются Hibernate. Обновление проверяется
в `CabinetApiTest`, как и роли, чужие группы, оценки, multipart, письма и Swagger.

## Устройство авторизационного слоя

- `SecurityConfig` содержит явный список публичных операций и правила RBAC.
  Остальные маршруты, включая новые операции под `/auth`, требуют аутентификации.
- `AuthenticationUserService` загружает учётные данные для Spring Security.
  `UserService` управляет профилем, email и паролем.
- `JwtCore` подписывает и проверяет JWT. `TokenFilter` определяет пользователя
  по обязательному `uid`, а текущую роль получает из БД. Поле `sub` сохраняет email
  для совместимости с выпущенными токенами; смена или повторная регистрация
  адреса не меняет владельца JWT. Обязательны подпись и срок действия `exp`.
- `AuthService` координирует вход, обновление пары токенов и выход.
  Ротация refresh-токена и создание access-токена выполняются в одной транзакции.
- `RefreshTokenService` и `TokenService` хранят только хеши токенов. Изменения
  сериализуются блокировкой строки пользователя, затем строки токена. Это
  предотвращает повторное использование токена и гонку logout с обновлением
  другой сессии того же пользователя.
- `SecurityErrorHandler` возвращает JSON `ApiError` для 401 и 403 из фильтров,
  как и `GlobalExceptionHandler` для ошибок контроллеров. Ошибки refresh-токенов
  сохраняют существующий HTTP-статус 400.

Logout отзывает все refresh-токены пользователя и допускает повторный вызов.
Смена и сброс пароля также отзывают refresh-токены; смена пароля дополнительно
отменяет ранее выданные ссылки сброса. Уже выданные access-токены действуют до
истечения срока (15 минут). Вход до подтверждения email разрешён; чувствительные
операции проверяют подтверждение через `CurrentUserService`.

## Ключевые бизнес-правила

- Email уникален; никнейм — нет. Подтверждение email требуется для чувствительных
  операций (заявки на роль, активация лицензии, синхронизация, работа с группами).
- Лицензия действует 365 дней; ключ активируется один раз (с блокировкой от гонок);
  для синхронизации симулятора требуется действующая лицензия.
- Приглашение в группу действует 7 дней; просроченные помечаются `EXPIRED`.
- Основная оценка = лучшая попытка (`best_score`); число попыток не ограничено.
- Оффлайн-события старше 14 дней при синхронизации отбрасываются.
- Студент принадлежит одному вузу; группа принадлежит преподавателю. Старые группы
  LMS связаны со справочником вузов, группы личного кабинета хранят организацию текстом.

## Безопасность

JWT + refresh-токены (ротация и отзыв при logout), Argon2, RBAC, обязательное
подтверждение email, аудит-логирование изменений (`audit_log`). HTTPS
обеспечивается на уровне reverse-proxy (nginx) при развёртывании.

## Схема БД

Управляется Hibernate (`ddl-auto=update`), включая обязательные индексы из
спецификации (через `@Table(indexes=...)`). `init.sql` намеренно не создаёт
таблицы, чтобы избежать рассогласования схемы.

Новые базы не создают удалённые неиспользуемые таблицы `verification_documents`
и `university_change_requests`. В существующей БД `ddl-auto=update` не удаляет
исторические таблицы и записи. Очистка кода не содержит `DROP TABLE`.
